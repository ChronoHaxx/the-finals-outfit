# Reconstruction execution plan

Accepted on 8 September 2026. Implementation is underway following the three-coat shader preview and pipeline audit.

The objective is a faithful outfit viewer across the catalog: correct meshes and body variants, material appearance, valid outfit combinations, hiding and garment fitting, followed by dynamic effects and acceptable runtime performance. The current web viewer remains the delivery target. Exact agreement with the game remains a validation goal, not an established property of the current renderer.

The main efficiency decision is to fix shared data and behavior, then expand coverage in batches. Material reconstruction and outfit assembly both depend on a faithful asset pipeline. Culling is part of the foundation milestone.

**Initial audit that established this order**

- The current catalog contains 2,866 items. 2,531 reference local meshes, representing 847 unique GLBs. File presence does not establish visual correctness.
- A JSON-header audit of all 847 GLBs found no `TANGENT` attributes and no morph targets. 468 files contain a second UV set, and 724 contain vertex colours. Different shader families may require different attributes; a missing second UV set is not automatically an error.
- The installed UEFormat importer skips original tangent data. `scripts/convert-meshes.py` also explicitly sets `export_morph=False`. The new direct DTO/GLB path addresses these omissions for the representative set above.
- The saved customization file contains 3,559 entries, of which 1,412 contain inferred hide-mesh tags and 2,273 contain inferred shape tags. These counts describe name-derived clues, not decoded rules or confirmed coverage of the catalog.
- `scripts/extract-customization.mjs` classifies printable name tokens and guesses under-layer associations. It does not recover complete property relationships, conditions or shape weights. These results must not become authoritative outfit rules without further validation.
- The catalog currently supplies no `model.hides` values. The rig combines generated body masks but still has an unimplemented mesh-hiding hook. Saved culling audit passes mean only that a mask exists and is non-empty; they do not establish correct outfit combinations.
- The first three coat surface previews used older meshes. They now use fresh preserved meshes by default in the recovered development path; matched in-game appearance has not yet been established.

**1. Establish a source inventory and preserve the necessary data**

Use one recorded game build for each coherent output set. Map catalog items to source packages, all relevant meshes/body variants, material sections, parent materials, shader variants and customization records. Reuse the working CUE4Parse extraction and existing catalog tooling. Record whether each relationship is decoded, inferred or unresolved.

Group shader work by actual compiled variants and required features, as well as parent material names. Count how many items each missing feature affects. This supplies the priority order and replaces the current subjective completion estimate with coverage measurements.

On a small representative set, preserve source normals, tangents and handedness, required UVs, vertex colours, material sections, skeleton/bind data and available morph targets. Validate coordinate conversions and attribute correspondence. GLB can carry tangents and morph targets; the current omissions are in our conversion path. Original game material and customization properties can remain in a separate manifest. See the [glTF specification](https://github.com/KhronosGroup/glTF/blob/main/specification/2.0/Specification.adoc).

Acceptance: traceable source-to-viewer records and verified attribute preservation for the selected cases. Broad reconversion starts after this path is validated. Generate a separate versioned output set so the existing preview remains available for comparisons.

**2. Validate one complete outfit and representative interactions**

Develop two components against the same source records. The material component evaluates the recovered surfaces. The outfit component determines which parts, variants and attachments are present, which regions are hidden, and which shape adjustments apply.

Treat culling as several behaviors: body coverage, clothing overlap, accessory visibility, alternate meshes, and deformation where the source supports it. A body mask alone cannot represent all of these. Investigate structured customization properties and referenced shape data before adding new inferred rules.

Choose representative interactions such as coat/shirt, sleeves/gloves, trousers/boots, hair/headwear and coat/back accessories. Include more than one pose and viewing angle, and establish body-variant cases early. A small set of matched in-game references will be needed to distinguish actual defects from differences in camera and lighting.

Acceptance: an end-to-end outfit with correct material bindings, geometry and demonstrated assembly behavior, plus repeatable interaction cases. Tests must detect both visible intersections and excessive hiding that creates holes.

Run small feasibility checks for demanding features such as hair, eyes, transparency and cloth-specific shading during this milestone. Discover any fundamental browser-renderer limitations before investing in bulk material ports. Keep rendering differences explicit and test proposed global corrections against multiple materials.

**3. Expand according to measured reuse**

Replace the three-item selection with discovery-driven reconstruction. Resolve each material's parent chain, parameters and textures automatically; translate supported variants and report unsupported operations or missing inputs explicitly.

Prioritize fixes by how many items they affect, how much other work they unblock, and the uncertainty involved. Add a small diverse batch for each new feature, validate it, then process the remaining matching items. Individual overrides need a documented source or reference and a regression case.

Acceptance: a coverage report connecting each item to supported material features and assembly rules, with a specific reason for every unresolved case. A successfully loaded asset is tracked separately from one whose appearance and interactions have been verified.

**4. Close remaining fidelity and runtime gaps**

Complete the remaining material families and renderer behavior in the order established by the inventory. Extend body variants, poses, garment deformation, animation, cloth simulation and dynamic material effects as required by the source. Keep these on the full-completion backlog even when an earlier static-viewer milestone is usable.

Measure memory, loading time and frame time on representative full outfits. Preserve a faithful local reference output before deriving compressed or simplified delivery assets. Confirm that optimizations retain the verified appearance and behavior.

Acceptance: remaining features have explicit validation cases, supported outfit interactions pass, and delivery performance meets recorded targets. Exact visual-parity claims require matched references and declared tolerances.

**Working practices that reduce repeated effort**

- Cache outputs by source hashes and pipeline version. Rebuild changed dependencies and rerun affected checks; use broader checks for changes shared across the viewer.
- Run inexpensive integrity and binding checks on every item. Select expensive render cases to cover shader features and outfit interactions, with focused combinations for rules involving several items. Review new features and detected regressions visually.
- Keep separate progress measures for source resolution, mesh preservation, recovered materials, assembly behavior, reference validation and runtime delivery. Count uncertainty explicitly.
- Extend the existing scripts and test harness before adding new infrastructure. Give each investigation a concrete question, a small sample and a success or failure result.
- Once the shared interfaces and examples are stable, add contributor setup instructions and small reproducible issues. Source code and synthetic fixtures can support contributions while extracted assets stay local. Contribution tooling should support the reconstruction work rather than become a separate product effort.
